# SMOTE keep/discard verdict — `testbed` track

Generated by `python -m src.smote_experiment`, which writes the numbers below
to `smote_testbed.json`. Both arms (class-weighted baseline, SMOTENC) are
trained inside that one run on the same train/test split and the same
LightGBM hyperparameters `src/model.py` uses — a paired comparison, not two
numbers from different code paths.

## Why `testbed`, never `full`

`src/model.py`'s own docstring: on `full`, class weighting is "very nearly a
no-op … a model at 0.999 macro-F1 has no minority-class recall left to
recover." Running SMOTE against a track with essentially no imbalance-driven
error to fix would produce a content-free "no measurable effect" result.
`testbed` (rung G) is where real minority-class confusion exists — see
`shap_interpretation.md` — so it is the only track this comparison can say
anything about.

## Method

- Feature set: `testbed` (27 columns, 8 categorical). Plain SMOTE cannot
  interpolate categorical columns, so **SMOTENC** was used —
  confirmed against the real training frame (dtype check + a trial
  `fit_resample`, ~7s on 48,000 rows) before committing to it.
- Categorical columns SMOTENC resampled: `customer_segment`, `country`,
  `platform`, `device_type`, `payment_method`, `return_reason`,
  `shipping_carrier`, `product_category`.
- SMOTENC resamples only the **training** fold (48,000 → 134,860 rows, 4
  classes balanced to 33,715 each). The test set is never resampled — both
  arms are scored against the same, real, class-imbalanced 12,000-row test
  set `src/evaluate.py` uses everywhere else.
- `RANDOM_STATE = 42` for the split, SMOTENC, and both LightGBM fits.

## Result

| | macro-F1 | accuracy |
|---|---|---|
| Class-weighted baseline | 0.8967 | 0.9297 |
| SMOTENC | 0.8944 | 0.9283 |
| Δ | **-0.0023** | -0.0014 |

Per-class recall (baseline → SMOTENC):

| class | baseline | SMOTENC | Δ |
|---|---|---|---|
| Fraudulent Return | 0.9676 | 0.9694 | +0.0018 |
| Legitimate | 0.9409 | 0.9449 | +0.0040 |
| Policy Abuser | 0.8600 | 0.8515 | -0.0085 |
| Wardrobing | 0.8973 | 0.8609 | **-0.0364** |

SMOTENC does not trade a majority-class precision loss for minority recall
gain (the failure mode the verdict rule specifically checks for) — it is
simpler than that here: Wardrobing recall gets *worse* under SMOTENC, and
the other three classes move by less than half a point in either direction.
The synthetic-neighbor interpolation on this feature set is not surfacing
real minority-class signal; on a couple of the (already-least-informative,
by ablation-ladder construction) `testbed` features, it looks to be
smoothing over the boundary Wardrobing depends on.

## Verdict: **DISCARD**

macro-F1 moved by -0.0023, in the wrong direction and inside noise for a
12,000-row test set — nowhere near the ±0.01 margin that would justify
adding a resampling step. Class weighting is already in the pipeline at zero
extra inference-time cost and with a one-line explanation
(`compute_class_weights`, inverse class frequency). SMOTENC would add a
second hyperparameter surface (`k_neighbors`, `categorical_features`,
which columns to trust as "interpolatable"), ~7s of extra pipeline time, and
a synthetic-neighbor step that is harder to explain to a panelist in a
five-minute pitch — for a result that is flat-to-negative.

This confirms, with real numbers, what `docs/ARCHITECTURE.md` §9.2 predicted
before any of this was measured: *"SMOTE at this ratio and sample size is a
two-hour experiment with a likely-negative result, not a day of work."* It
was.
